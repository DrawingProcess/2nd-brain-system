# OpenRouter 모델 추천 및 inbox 승격 작업 비용 추정

**작성일**: 2026-08-01
**작성자**: Claude Code
**목적**: Hermes에 OpenRouter API 키가 등록됨에 따라, `inbox/` → `raw/articles/`
승격 작업(`docs/260801_03` §2.2 "자동 경로 B")을 자동화할 때 쓸 가성비 모델을
추천하고, 문서 1건을 처리하는 데 드는 토큰/비용을 추정한다. Anthropic 키는
인증 실패(401), OpenAI 키도 인증 실패(401)로 확인되어 OpenRouter로 전환함.

---

## 1. 전제: 원문을 그대로 curl하면 안 됨 (비용 설계상 가장 중요한 제약)

이번 세션에서 두 기사(Apple, Dow) 원문을 직접 `curl`로 받아봤을 때 HTML
크기가 각각 **약 600~760KB**였다. 만약 크론 에이전트가 이 raw HTML을 그대로
자기 컨텍스트에 읽어들이면, 기사 1건당 대략 150,000~200,000 토큰이 그냥
낭비된다 — 모델 판단 비용과 무관하게 구조적으로 비싸진다.

`finance-morning-digest.py`는 이미 이 문제를 결정론적 코드(`fetch_teaser()`)로
피하고 있다 — `curl` 후 정규식으로 `og:description`/JSON-LD만 뽑아
1~2문장만 반환한다. **inbox 승격 job도 동일한 원칙을 따라야 한다**: 에이전트가
직접 `curl <url>`을 실행하게 하지 말고, `finance-morning-digest.py`의
`fetch_teaser()`/`fetch_excerpt()` 로직을 재사용하는 작은 헬퍼 스크립트
(예: `fetch-article-excerpt.py <url>`)를 통해 **추출된 텍스트만** 에이전트
컨텍스트에 들어오게 해야 한다. 아래 비용 추정은 **이 헬퍼 스크립트를 쓴다는
전제** 하에 계산한 것이다 — 이 전제가 깨지면(에이전트가 raw HTML을 직접
받으면) 아래 추정치는 100배 이상 틀어진다.

## 2. 토큰 추정 방법론

실측 데이터가 있는 유일한 소스는 2026-08-01 03:00 KST 크론 실행 로그
(`~/.hermes/logs/agent.log`, `docs/260801_01` §5에서 분석한 바로 그 실행)다.
이 실행은 기사 2건을 처리하며 API 호출 10회, 총 입력 282,238 토큰 / 출력
13,851 토큰을 썼다 — 다만 이 실행은 `execute_code` 차단 이후 반복 재시도가
섞인 **비정상 실행**이라 그대로 쓰기엔 과대추정이다.

정상 실행(재시도 없음)을 가정해 기사 1건당 필요한 턴을 다시 추정하면:

| 턴 | 작업 | 비고 |
| --- | --- | --- |
| 1 | inbox 파일 읽기 | 짧음 |
| 2 | `fetch-article-excerpt.py <url>` 호출 | 추출 텍스트만 반환(수백~2천자) |
| 3 | 요약 작성 + 임시 파일에 기록 | 출력 토큰 다소 큼 |
| 4 | `file-article.py` 호출 | 결과 한 줄 |
| 5 | inbox 파일 삭제 | 짧음 |

관측된 로그에서 첫 턴 입력이 이미 18,000~26,000 토큰이었다(시스템 프롬프트
+ 전체 툴 스키마 + `AGENTS.md`/`SCHEMA.md` 주입 — 이건 모델과 무관한 고정
오버헤드). 이를 기준으로 턴이 진행될수록 대화 이력이 누적된다고 보수적으로
가정하면:

- 입력 합계 ≈ **112,500 토큰**, 출력 합계 ≈ **3,050 토큰** (기사 1건 기준)

여러 건을 한 실행에서 연속 처리하면 대화 이력이 계속 누적되므로 건당 한계
비용은 이보다 조금씩 늘어난다 — 아래 표는 "각 건이 독립 실행"이라는 단순화된
가정이며, 실제로는 다소 보수적(=낮게 잡힌) 추정치일 수 있다.

## 4. 비용 추정 (기사 1건 / 일일 배치 9건 / 30일)

9건은 오늘 실제로 처리한 배치 크기(§260801_02 §4)를 그대로 사용한 것이며,
매일 이 정도 물량이 들어온다는 보장은 없다 — RSS에 새 기사가 없으면 0건.

| 모델 | 건당 비용 | 9건/1회 | 30일 누적(9건/day 가정, 상한선) |
| --- | --- | --- | --- |
| `moonshotai/kimi-k2-0905` | $0.075 | $0.68 | **$20.28** |
| `moonshotai/kimi-k2` | $0.071 | $0.64 | $19.21 |
| `z-ai/glm-4.6` | $0.062 | $0.56 | $16.83 |
| `deepseek/deepseek-chat-v3.2` | $0.032 | $0.28 | $8.50 |
| `qwen/qwen3-235b-a22b-2507` | $0.012 | $0.11 | $3.19 |

30일 누적은 "매일 9건씩 들어온다"는 상한선 가정이다. 실제로는 RSS 신규
건수가 날마다 0~9건 정도로 들쭉날쭉할 것으로 예상되므로, 실사용 월 비용은
표의 30~70% 수준일 가능성이 높다(추정, 실측 아님).

## 5. 추천

**`moonshotai/kimi-k2-0905`를 1순위로 추천**한다. 이번에 해결한 문제의 본질이
"로컬 모델이 결정론적 스크립트 호출을 안정적으로 이행하지 못함"이었기 때문에,
가장 저렴한 모델보다 **툴콜 지시 이행 신뢰도가 검증된 모델**을 우선하는 게
맞다고 판단했다. 월 20달러 미만이면 이번 문제 재발 방지 목적에는 합리적인
비용으로 보인다.

다만 확신은 아니므로, 실제로 `finance-inbox-promote` job을 만들 때
`deepseek/deepseek-chat-v3.2`(비용 1/2 이하)도 같이 몇 차례 테스트해 두
모델의 성공률을 비교해보고, 문제없으면 더 저렴한 쪽으로 바꾸는 것을 제안한다.
